## 卡片 015：电梯实现边界

**问题**

电梯是否需要专用 Node/World 类型，以及厅门、轿厢门、请求队列和停留过程如何表达？

**我的理解（已确认）**

电梯箱是普通 `Object`，通过 `transport_device`、`contain` 等能力和 `process_bindings` 表达。电梯井是独立静态结构；轿厢内部按钮和轿厢门属于电梯箱；每层只有一个厅门，厅门和上下召唤按钮属于对应楼层房间。保留 `elevator_system_id`、`elevator_car_id`、`shaft_id`、`floor_id` 字段，当前只实现单部电梯。

请求按到达顺序决定 `idle` 初始方向；同时到达时向上优先。当前方向上的请求按楼层顺序处理，不跳站；反方向请求留到反向处理；同一楼层请求合并。电梯到站后进入 `opening -> dwelling -> closing`，开门瞬间解除通行阻塞并熄灭已服务按钮，停留默认 2 个 tick；停留期间重复请求重置计时，关门期间请求触发重新开门。轿厢内对象保持 `inside(cabin)` 的局部关系并随轿厢变换。

**当前实现**

`backend/runtime/elevator.py` 提供纯调度和门状态规则，`process_rules.py` 在统一时钟中推进；电梯仍通过普通 `press` Action 进入请求队列。

> 规则：每张卡片先写问题，再写当前实现采用的理解。实现不因卡片停滞；用户确认后再修订协议。

## 卡片 001：物理后端的默认选择

**问题**

Web 端第一版使用哪种物理实现？

**我的理解（已澄清）**

## 卡片 007：Web 承载面预览的几何来源

**问题**

承载面目前可能来自根物体的渲染包围盒，也可能来自结构部件（例如抽屉或货架槽）的独立碰撞体；最终协议是否要为每个 Link 显式提供局部承载面尺寸、朝向和网格原点？

**我的理解（已确认）**

区分两种面：根 Link 的 `can_support=true` 表示物体上表面是承载面，关系是 `on`；component Link 的 `can_contain=true` 表示抽屉、货架槽等内部底面是容纳面，关系是 `in`。容纳面不是四周的墙，而是 Link 明确声明的局部底面/容纳原点。两者都应在 Link 的结构数据中声明尺寸、局部原点和网格；当前旧场景仍允许 Web 用包围盒作过渡预览。Q/E 请求携带命中 Link 和命中点，由后端确认最终关系与局部变换。

## 卡片 008：前端预览单位与坐标适配

**问题**

Core 协议采用 Z-up、米制世界变换，而当前 Three.js 场景仍以 Y-up 表现并在局部位置使用米；放置预览是否要在 Web 端增加显式坐标适配层？

**我的理解（已澄清）**

协议层需要单独的坐标适配器，不改变 Core 的 Z-up 约定。Web 端已增加纯函数适配器，将协议坐标转换为 Three.js 的 Y-up 坐标；历史布局渲染和旧的 `x/y` 平面数据暂不整体切轴，待场景迁移验证后再把 snapshot 的 `world_transform` 全量接入渲染。

**实现证据与边界**

历史布局是旧数据格式：它把 `x/y` 当作平面网格的两个方向，`z` 表示高度；Three.js 旧渲染代码也直接把第二个平面方向放在自己的 `z` 轴上。所谓“暂不整体切轴”，是指不把这批旧布局字段逐个重写成新协议坐标，否则所有旧物体会整体错位。新协议的 snapshot 已统一为 Z-up，Web 通过一次坐标适配器转换到 Three.js Y-up；旧布局只在导入/投影边界转换。

Snapshot 现在返回 `coordinate_system={units:m, handedness:right, up_axis:z, rotation:quaternion_xyzw}`，Web delta 也会保留该字段。

## 卡片 009：布局坐标与资产原点的关系

**问题**

历史布局中的 `x_cm/y_cm/z_cm` 表示物体包围盒的左下角、几何中心，还是资产根节点原点？`world_transform.position` 应该使用哪一种语义？

**我的理解（建议采用）**

旧布局的 `x_cm/y_cm` 是物体底面包围盒在平面上的左下角锚点，`z_cm` 是底面高度；旧渲染时再加半宽、半深、半高得到几何中心。

对当前阶段的新资产，统一约定：Object root 的局部原点位于物体外包围盒中心。因此：

- `world_transform.position` 表示 root 几何中心；
- 旋转围绕物体中心进行；
- 放置到地面或承载面时，运行端用物体高度的一半计算支撑高度；
- 旧布局导入时，把左下角锚点加上半宽、半深、半高，转换成 root 中心。

这个约定只适用于 Object root。component Link 的原点仍由 `Joint.origin` 或容纳 Link 的局部容纳原点决定；关节轴、抽屉底面和门铰链不要求位于部件几何中心。若未来导入外部资产必须使用非中心原点，则通过资产几何的局部偏移表达，不改变世界协议。

## 卡片 010：视觉效果声明与语义兼容

**问题**

视觉动画（发光、气流、蒸汽、破损等）是否继续由 Web 根据 `semantic_type` 特判，还是由资产声明并通过 snapshot cue 下发？

**我的理解（已澄清）**

动画不需要再建一个笼统的“动画 Node 类”，而应按来源分三类：

1. **Joint motion**：门、抽屉、轮子、升降件的平移/旋转，由 joint state 驱动；
2. **Visual effect**：发光、气流、蒸汽、水滴、火焰、破损等，由状态/能力导出 `visual_cues`，前端决定材质、粒子和循环动画；
3. **Interaction feedback**：描边、高亮、放置预览、举手等纯交互表现，只存在于前端，不进入世界语义。

移动和真实下落属于前端物理表现；后端只确认语义状态和最终关系。三类表现可以共享前端的 `AnimationAdapter`，但不增加 Core 里的具体动画继承层级。

## 卡片 011：动作兼容规则的迁移边界

**问题**

当前运行时仍支持旧场景中的语义字段（例如 `semantic_type`、旧容器属性和模板回退）。这些兼容规则何时可以删除，是否需要一次性迁移全部历史场景？

**我的理解（已澄清）**

“语义兼容分支”不是新的架构概念，而是为了读取旧场景保留的 fallback。例如：节点没有完整 capability 时按 `semantic_type=light/door/...` 推断行为；节点没有内嵌 `process_definition` 时回退到 Generation 模板；旧布局只有 `x_cm/y_cm/z_cm` 时按尺寸推导 root transform；旧容器字段仍被读取。它们让历史数据继续运行，但新资产不应依赖它们。迁移完成后可逐条删除并补回归测试。

## 卡片 012：前端移动预测与语义确认

**问题**

Web/Unity/Isaac 是否可以在后端响应前预测连续移动和物理碰撞？预测失败或与后端位置不一致时由谁纠正？

**我的理解（已澄清）**

前端可以先把玩家胶囊体向 W/A/S/D 方向移动一小步，让画面立即响应；这叫预测。随后请求后端 `move_step`，后端依据自己的语义边界、门状态和房间连通返回权威位置。两者不同就把画面校正到后端位置。预测值不能写入语义图，也不能自行宣布“已经进入房间”或“门可以通过”。
